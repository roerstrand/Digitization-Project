# ADR-001: Swedish and English versions of the site

- **Status:** Accepted, amended by [ADR-002](ADR-002.md) (Swedish now lives at the root and English under `en/`)
- **Date:** 2026-11-15

## Context

The site is written in English, while its subject, its source material (catalogs from Malmö City Library, newspaper clippings from Malmö City Archive) and a large part of its audience are Swedish. A language toggle is required for all content: about 13,000 words across 16 pages (8 main pages, 4 metadata pages, 4 TEI pages).

The site is static HTML on GitHub Pages with one shared stylesheet (`css/main.css`) and one shared script (`scripts/main.js`). There is no build step and no framework.

## Alternatives

### A. Separate Swedish pages generated by a build script

Swedish pages live under `sv/` with the same file names (`sv/baltictower.html`). A Node script (`tools/build-sv.mjs`) reads each English page, replaces its text segments with translations from `i18n/sv/<page>.json`, rewrites asset paths, sets `lang="sv"`, and writes the result. The toggle is an ordinary link to the same page in the other language.

- **Pros:** each language has its own URL with `hreflang`, so search engines index both; works without JavaScript; structure and styling stay in one place (the English source), so a layout change is made once and regenerated; translations are plain data, separate from markup.
- **Cons:** a build step must be run after editing an English page; a changed English sentence leaves its translation unmatched until the JSON is updated (the script reports this).

### B. Both languages inline in the same HTML

Each text appears twice (`<span lang="en">` / `<span lang="sv">`) and CSS hides the inactive one.

- **Pros:** one file per page; instant switching without reload; no build step.
- **Cons:** every page doubles in size; hidden text that is hidden incorrectly is read by screen readers and indexed twice; every edit touches interleaved markup; languages cannot be worked on independently.

### C. JSON dictionary applied by JavaScript

Elements carry `data-i18n` keys and `scripts/main.js` swaps in Swedish strings at runtime.

- **Pros:** clean HTML; all strings in one place per language; easy to add further languages.
- **Cons:** no Swedish without JavaScript; search engines see only English; a flash of English before the swap; keys drift from markup as pages change.

## Decision

Alternative A. Swedish pages are generated into `sv/` from the English pages and `i18n/sv/*.json` by `tools/build-sv.mjs`. Interface strings created by `scripts/main.js` (menu, table of contents, viewer, back to top, footer additions) are translated in the script by reading `document.documentElement.lang`.

The transcriptions on the TEI pages and the Swedish headlines in the press timeline are Swedish source material and are kept as they are in both languages; only the surrounding interface and commentary are translated.

## Consequences

- After editing an English page, `node tools/build-sv.mjs` must be run and the generated `sv/` files committed. The script lists English segments that have no translation, so gaps are visible.
- `sv/` is generated output and is never edited by hand.
- Each page links to its counterpart with `<link rel="alternate" hreflang>`, and the language toggle sits in the fixed controls next to the theme switch.
- The approach scales to further languages by adding `i18n/<lang>/` and a target folder, without touching the English pages.
